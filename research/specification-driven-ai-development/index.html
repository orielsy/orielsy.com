From Prompts to Project Memory: Spec-Driven Development for Coding Agents

A repository-grounded look at using version-controlled specs, decisions, and project rules as durable memory for coding agents across long-running software work.

Conversation Context Is Not Project Memory

A conversation is useful working context: objectives, tradeoffs, corrections, and discoveries. It is not durable project memory.

A new session or tool may see only the repository, so durable decisions need version-controlled artifacts beside the implementation.

A project should not depend on one conversation remaining available forever.

A Real Failure: When an Old Decision Came Back

I have already seen the opposite fail.

During work on this site, we had established experience with reusable UI components, component architecture, frontend patterns and systems, UI architecture, and engineering standards—but not formal design-system ownership.

Later, the homepage contained this line:

“15+ years of experience designing scalable web architectures, design systems, and enterprise platforms.”

The wording was plausible and polished. It was also unsupported.

This was a context-persistence failure, not primarily a coding error.

The fix had two layers: correct the homepage and correct the durable project memory. The constitution now explicitly blocks that design-systems claim unless the experience is established later, and specs/001-site-foundation/spec.md carries the same positioning constraint.

“Less likely” is intentional. A repository rule cannot guarantee agent behavior, but it gives later sessions something durable to recover.

Externalizing Intent

orielsy.com uses a lightweight Spec-Driven Development structure with several scopes of project memory.

Constitution: project-wide invariants

.specify/memory/constitution.md holds rules that should survive individual features and sessions: factual-accuracy constraints, content taxonomy, repository-link rules, static-first architecture, and editorial voice.

For this article, one rule matters especially: quantitative claims require evidence, proposed architecture must not be written as implemented work, and source code outranks generated prose when they disagree.

Feature specs: desired behavior and scope

A feature spec narrows the requirement. specs/003-content-publication-gating/spec.md, for example, defines how unpublished Research and Project entries remain visible without exposing unfinished body content or becoming indexable published pages.

That durable behavior survives changes to the card or interaction design.

Plans and tasks: implementation and execution state

The same feature’s plan.md translates the requirement into technical strategy; tasks.md turns that strategy into executable work.

Requirements can remain stable while implementation strategy and task state change.

ADRs: durable reasons

Decision records preserve choices whose rationale is not obvious from code. docs/decisions/003-manual-production-publishing.md, for example, records that pushing source does not publish the site; production deployment is an explicit npm run live action.

That intent should not have to be rediscovered from package scripts.

The Agent Entry Point

AGENTS.md stays deliberately thin. Its job is to route an agent into the project’s existing memory:

It is a routing layer, not a mega-prompt. Copying every rule, requirement, task, and decision into one instruction file would recreate the context problem in another form.

The goal is discoverability at the right scope.

Updating the Source of Truth Before the Code

When a requirement changes materially, the durable artifact should change with the implementation rather than leave stale intent behind.

Publication gating provides a concrete example. When unpublished cards changed from non-clickable summaries to inline status interactions, the feature spec, README, publication-gating ADR, and URL/SEO policy changed with the implementation.

The next agent therefore inherits the requirement instead of inferring it from whichever component happens to exist.

What This Does Not Solve

Version-controlled memory still has failure modes:

  • Wrong specs stay wrong. Durability does not make an assumption true.
  • Specs can become stale. Implementation can outrun the artifact.
  • Agents can misread explicit context. Documentation reduces ambiguity; it does not eliminate interpretation errors.
  • Documentation can become noise. Overlapping or redundant artifacts make retrieval harder and can disagree.
  • Specifications do not replace tests. Requirements and passing behavior are different evidence.
  • Human judgment remains necessary. Engineers still decide what becomes durable, which artifact owns a decision, and whether implementation satisfies intent.

The system only helps if its memory is maintained.

Where This Could Go Next

Once the project can remember, an agent still needs to decide which parts of that memory matter for the current task.

The next research layer is selection and delivery:

  • task-aware selection of relevant specs, decisions, and repository patterns
  • context delivery through MCP or another explicit mechanism
  • repository-specific routing that avoids loading the entire memory at once

An unpublished Repository Context Engine for Coding Agents concept explores that direction; it remains proposed architecture.

For now, the useful result is simpler: important decisions can outlive the conversation that produced them.
