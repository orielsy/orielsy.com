Reading depth

The interface knows the state. The guidance knows the why.

A user configuring a Data Connection may need an explanation scattered across documentation or release notes. This research asks what happens when the application selects applicable authored knowledge at that point of need—without letting documentation, or a future AI layer, decide product truth.

Adaptation without inference

Phase 1 compares standard and adaptive forms under the same scenario, application state, and required-field validation. The adaptive form selects small authored fixtures using explicit conditions such as version, simulated familiarity, and field state. No LLM or remote inference is needed. Whether a fragment applies is one question; whether the interface may explain, guide, or offer a value is a separate policy decision.

Evidence sets the ceiling

With several compatible connections, the user’s intent is unresolved: explain the requirement or guide attention, but do not guess. With exactly one compatible connection, the interface may offer “Use connection”; the user must accept it. Familiarity and version can change the explanation, not validity. Once a valid selection exists, missing-field intervention ends.

A reference experiment, not an outcome claim

The scenarios are fixed, the knowledge is authored fixture data, and familiarity is simulated. There is no document ingestion, semantic retrieval, behavioral learning, or measured UX improvement here. Governance of stale or conflicting guidance remains open. Later inference might map intent or rank candidates after deterministic filtering, but its output would still be checked against application truth and response policy.

The Documentation / Interface Disconnect

Enterprise software usually treats product knowledge and product behavior as separate systems. The application knows its state. Validation knows which values are required. Documentation explains concepts, release notes describe version changes, and implementation guides tell users how to make a choice. Those sources often live outside the interface that needs them.

One possible detour is familiar in shape: a user reaches a configuration field, encounters uncertainty, leaves the application to consult documentation, interprets what they find, and returns to the task. This is the design problem illustrated below, not a measured journey in this experiment.

Move the knowledge, not the user.

The opportunity is not simply to move documentation into a tooltip. A static tooltip gives every user the same explanation. Here, explicit conditions select a note for the current version, simulated familiarity, and field state; separate application rules determine whether the interface may explain, guide, or offer a value. This does not determine what an individual user actually needs.

The reference experiment makes this concrete at one required Data Connection field. A standard form and an adaptive form receive the same version, simulated user familiarity, compatible options, and validation rule. The adaptive form can explain a missing choice, vary authored guidance, or offer the sole compatible connection for the user to accept; it cannot choose among several. Start with Application Truth

The first architectural rule is simple: the application remains authoritative. Documentation can explain a rule, but it should not redefine it. Product knowledge can enrich the experience, but deterministic business logic should remain deterministic.

Taking that rule seriously separates the experiment into seven concerns. They fall into three groups, and the groups are also the order in which a decision is made: the application establishes what is true, authored knowledge is selected against that truth, and only then does the interface decide how strongly to respond and how to show it. The later groups depend on application truth, but they do not redefine it. Phase 1 makes these decisions without inference.

Keeping these responsibilities visible gives later AI capabilities a clean place to enter without asking them to replace validation, compatibility rules, or product state.

Why Deterministic First?

A required field, a version-specific note, or a single compatible option is already knowable from application state and authored rules. Starting there lets Phase 1 test the separation between product truth, relevant guidance, and permission to intervene without introducing inference as another source of uncertainty.

01

It exposes the real architectural boundaries

If the system cannot clearly distinguish validation from product knowledge before AI is introduced, adding an LLM will hide the ambiguity rather than solve it.

02

It prevents AI from owning rules it should not own

Known constraints belong in code or configuration that can be tested directly. Generated text should not become the source of truth for required fields, compatibility, permissions, or other deterministic behavior.

03

It creates a baseline for future inference

A future semantic system should improve ambiguity resolution and relevance selection. Its behavior should be comparable with a deterministic baseline.

Structured Product Knowledge

The reference implementation does not ingest real documentation yet. Instead, it models small authored knowledge fragments that approximate what a future ingestion or authoring pipeline could produce.

The fragments include a basic Data Connection summary, required-field help, a beginner-oriented concept explanation, version 4.2 guidance, and configuration-selection guidance. Each carries applicability information such as audience, version, and state conditions, plus provenance identifying whether it represents documentation or a release note.

Version-specific knowledge applies only when the product is at least version 4.2 and the Data Connection is missing. Beginner help applies only to a new user in the same missing-connection state.

Context selection, not context accumulation.

The goal is not to dump all related documentation into the interface. First narrow the available knowledge according to deterministic facts, then decide how much of it deserves to become interface behavior.

Knowledge Applicability Is Not Response Policy

Knowing something applies does not automatically determine what the interface should do with it.

Knowledge applicability asks whether authored information matches the current product state, version, and audience. Response policy asks how strongly the interface should intervene given that state, the validation result, available knowledge, and certainty of the evidence.

A version note can be relevant without deserving a modal. A beginner explanation can apply without changing validation. A configuration guide can apply while the interface still refuses to choose among several valid options.

This separation becomes especially important if semantic retrieval is added later. Retrieval can rank or discover relevant knowledge while response policy still decides whether the result becomes help text, a highlight, a suggestion, or an action.

UI Authority Should Follow Evidence

Stronger intervention needs a narrower, explicitly authorized basis; certainty about compatible options is not certainty about the user’s intent. A response policy might range from no intervention through explanation, help, highlighting, and guidance to an offer to use the sole compatible value. In Phase 1, accepting that offer is the user’s action; the interface does not silently set the field or perform an autonomous destructive action.

The critical boundary is between guidance and choice.

01
Explain

Expose the meaning of the field or a relevant version note.

02
Guide

Highlight the control and clarify the choice that remains.

03
Offer

Offer the sole compatible value for the user to accept.

If several Data Connections are compatible, the system can explain the requirement and guide the user toward the field, but it does not know which connection matches the user’s intent. It must not guess.

If exactly one compatible Data Connection exists in the controlled scenario, the interface may offer it as an explicit user-accepted action. The candidate count removes ambiguity among the available values; it does not establish the user’s intent or guarantee that the connection is appropriate for their task.

What Phase 1 Actually Shows

These are properties demonstrated by the deterministic reference implementation, not measured improvements in comprehension, task success, or safety.

Demonstrated in the reference implementation
  • Product knowledge can participate in interface behavior without owning business logic.
  • The interface can vary guidance without inference.
  • The count of compatible options constrains whether the interface guides a choice or offers one value for the user to accept.
  • Progressive help can be represented as an explicit response policy.
Proposed architectural implication

Inference may be useful where the application is genuinely ambiguous: interpreting freeform intent, ranking semantically relevant knowledge, adapting explanations, or bridging combinations that were not explicitly authored. Phase 1 has not evaluated those uses.

A future AI layer has a narrower job than “control the UI.”

The deterministic experiment suggests that inference should resolve ambiguity rather than invent application truth. That is a much smaller and safer responsibility than asking a model to infer the entire interaction model at once.

Limitations of the Current Experiment

Phase 1 is not a production adaptive-UX platform. Its product knowledge is authored fixture data, its compatibility scenarios are fixed demo data, and user familiarity is a simulation control rather than an inferred or persisted profile.

Intentionally not included

  • Document ingestion
  • Semantic search
  • Embeddings or vector retrieval
  • Natural-language intent resolution
  • Generated guidance
  • Telemetry or behavioral learning
  • Backend services or persistence
  • Authentication
  • WebLLM or MCP
  • Remote AI APIs

The experiment also does not answer how knowledge fragments are reviewed, stale release guidance is retired, conflicting sources are reconciled, or intervention quality is measured. Those are not omissions hidden behind the demo; they are deliberately outside the Phase 1 question.

Where AI Could Enter Later

The deterministic architecture gives future inference explicit seams. Optional inference could sit after deterministic filtering and before evidence reconciliation and response policy.

Natural-language intent resolution

Map a user’s language to the relevant product concept, while the deterministic resolver still checks current state before responding.

Semantic product-knowledge retrieval

Rank knowledge after filters such as version, environment, permissions, or feature availability have reduced the candidate set.

Explanation adaptation

Rewrite or compress an already-authorized explanation while preserving its facts and action boundary.

Where such inference would run is a separate, unevaluated question. Browser-local processing could keep some application context on the device; routing between browser, local service, and remote model would be a deployment decision, not another interface capability.

Inference should resolve ambiguity, not replace truth.

From Documentation Portal to Product Capability

The broader direction is not to eliminate documentation. Long-form documentation remains necessary for learning, implementation, troubleshooting, and reference. The opportunity is to stop treating it as useful only after the user leaves the product to search for it.

Some product knowledge can be structured with its concept, applicability conditions, audience, version, and provenance. Application state and response policy—not the knowledge fragment alone—determine whether and how the interface may act on it.

At that point, documentation is no longer only a destination. It becomes one input into interface behavior. The strongest version is not an interface that constantly talks: it becomes quieter when context is obvious, more explanatory when uncertainty is predictable, and more helpful only when the available evidence justifies it.

How adaptive can an enterprise interface become before AI is necessary?

In this reference implementation, far enough to tailor guidance and offer an unambiguous choice without inference. Whether that improves the experience—and where inference would add value—remains to be tested.
