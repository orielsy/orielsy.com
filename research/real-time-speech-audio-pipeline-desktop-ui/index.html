Reading depth

A caption is the last decision in a chain.

Live transcription is not just a model returning text. Audio must be captured, reduced, accumulated, transcribed, accepted, and rendered while each part operates under a different constraint. This paper begins inside the working speechBubbles system established by the project case study; it inspects what the current public source actually does at four boundaries.

Reduce the data; choose the wait

The capture format need not be the transport format. In the source, client-side downsampling and Int16 conversion change a 48 kHz stereo Float32 example from about 384 KB/sec of raw samples to 16 kHz mono Int16 at about 32 KB/sec before WebSocket overhead. That ~91.7% difference is arithmetic, not a measured bandwidth result. The service then accumulates fixed-duration chunks: shorter ones can return updates earlier with less linguistic context; longer ones offer more context but arrive later. Three seconds is the public backend default without an override, not an established optimum or a sliding window.

Follow the active path, not the repository inventory

VAD scaffolding exists, but the current public transcription path does not run it before Whisper. Instead, returned segments reach client-side filtering, which accepts nonempty text only when no_speech_prob ≤ 0.6 and temperature ≤ 0.8. This can suppress likely low-confidence text; it cannot promise that all phantom captions disappear.

Separation makes the next tests legible

Whisper inference runs through asyncio.to_thread() rather than blocking the service event loop. Caption layout and transitions follow their own Electron/Vue scheduling path, which still includes geometry reads worth investigating. Neither separation proves low latency, reliability, or smooth rendering. The next experiments are to wire and evaluate VAD, compare chunk strategies, and batch geometry reads before DOM writes.

Source grounding

The speechBubbles project case study establishes the working prototype, creator role, broadcast workflow, and system-level responsibility boundary. This paper begins inside that boundary and inspects four implementation paths: audio-format reduction, chunking, transcription filtering, and async inference/render scheduling.

Real-time speech UI is a pipeline problem. Capture, format reduction, buffering, inference, filtering, state, and rendering introduce different constraints, so the architecture is easier to reason about when those responsibilities remain separate.

The Audio Sample Rate Dilemma

Consumer audio hardware and browser AudioContext instances commonly operate at 44,100 Hz or 48,000 Hz using floating-point sample buffers.

Sending 48 kHz stereo 32-bit float audio directly would produce about 384 KB/sec of raw sample data before protocol overhead:

48,000 samples/sec × 2 channels × 4 bytes/sample = 384,000 bytes/sec.

Handling Low-Confidence Transcription Output

Continuous microphone input can cause Whisper to emit undesirable text during silence, ambient noise, or otherwise low-confidence audio. The public source currently addresses this primarily on the client after transcription.

Current Backend Behavior

whisper-api includes a VADFactory, PyAnnote dependencies, and a lazy get_vad() helper. However, the current public process_buffer() implementation does not invoke that VAD pipeline before model.transcribe().

Async Inference & UI Rendering

The backend uses asyncio.to_thread() around model.transcribe(), moving blocking inference off the async event loop. The same principle—keep blocking work off the responsive path—applies in the renderer.

CaptionsView.vue measures caption geometry after Vue’s nextTick(), then uses nested requestAnimationFrame() callbacks to apply the transition styles:

The current prototype still performs synchronous geometry reads when captions mount, including a second getBoundingClientRect() after style changes. That is acceptable as implementation evidence for the current prototype, but it is not presented here as an optimized rendering strategy; a production pass should batch geometry reads before DOM writes to reduce forced-layout risk.

Architectural Takeaways & Future Directions

The most defensible principle is specific: capture, blocking inference, acceptance policy, and rendering are easier to inspect when their ownership remains explicit. That separation does not establish a latency or reliability improvement by itself; it makes the different failure modes and optimization targets easier to locate.

The next experiments follow those boundaries: wire the existing VAD path into the active transcription flow, compare chunk-duration strategies rather than treating the current default as optimal, and batch caption geometry reads before DOM writes.
