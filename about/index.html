Principles

The working positions behind how I design interface systems, architecture, and emerging capabilities.

  1. 01State

    State Systems Over Screens

    Interfaces are more than the screens they render. I tend to start with the state model—what the system knows, how that state changes, where authority lives, and how the interface responds—before treating individual views as the architecture.

  2. 02Judgment

    Architecture Should Follow the Problem, Not the Tool

    Frameworks, runtimes, patterns, and abstractions are means to an end. I try to begin with the constraints of the system—its users, state, performance, longevity, team, and operating environment—and choose the architecture that fits rather than forcing the problem into a preferred technology.

  3. 03Abstraction

    Abstraction Should Remove Complexity, Not Relocate It

    Good abstraction should reduce the complexity a user or developer has to carry, not simply hide it behind another layer. I look for boundaries and interaction models that simplify the system while preserving the information and control people actually need.
