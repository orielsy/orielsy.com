A long-running conversation can still fit inside the model's context window while becoming a worse place to continue the work.

Useful history accumulates beside abandoned directions, replaced decisions, repeated explanations, contradictory instructions, and details that no longer affect the next action. Capacity is not the same thing as context quality.

Context Zen starts from a narrower question:

> **What state does the next capable agent actually need in order to continue correctly?**

The skill is an early context-engineering experiment. Its handoff behavior is defined as a public skill specification; its judgment about *when* to hand off is still provisional.

## Reconstruct State, Not Chronology

A transcript records what happened in order. Working state records what is true now.

Context Zen uses **context distillation** to mean reconstructing the smallest reliable state required to continue the work while intentionally dropping history that no longer has forward value.

  <ContextZenStateExtractionVisual />
</ResearchBreakout>

A useful handoff preserves the current objective, decisions still in force, relevant constraints, rejected approaches likely to be rediscovered, active artifacts, unresolved questions, and the immediate next step.

It can compress chronology, abandoned exploration, obsolete assumptions, repeated explanations, and agent self-commentary.

The goal is not the shortest summary. It is the smallest handoff that still preserves **correct continuation**.

Context Zen's lifecycle is deliberately simple: **Observe → Distill → Handoff**. Observation asks whether accumulated history is still helping. Distillation reconstructs authoritative state. Handoff packages that state for a fresh context.

## Judge When History Becomes Drag

Context Zen is opt-in. Once enabled, it evaluates context health during ordinary turns; that does not imply background execution. If the host has no background execution model, the skill does not pretend to be a daemon.

The difficult part is deciding when useful history has become contextual drag.

I do not want to fake precision here. Without a validated scoring model, v0.1 uses qualitative context-health states rather than a numeric threshold.

<ResearchBreakout mode="wide">
  <ContextZenHealthJudgmentVisual />
</ResearchBreakout>

Hard signals can inform the judgment: context load, turn count, active artifact count, or tool-result volume. None of them should force a handoff by itself.

The more consequential signals are semantic:

- retained context describes decisions that have already been replaced
- old and new instructions collide
- the agent rediscovers information the conversation already established
- important constraints become buried beneath unrelated history
- the agent acts on obsolete state
- the user increasingly corrects context drift
- a shrinking share of the retained conversation materially affects the next action

The current decision heuristic is a counterfactual:

> **Would a fresh capable agent with a faithful compact handoff probably have an easier time continuing correctly than the current agent has reasoning over the accumulated conversation?**

That is a working heuristic, not a validated handoff threshold.

## Activation Follows the Work

If activation belonged only to one conversation, Context Zen would disable itself every time a handoff successfully moved the work elsewhere.

Instead, v0.1 attaches activation to a **continuation lineage**: the chain of work that survives across handoffs.

The handoff carries a small marker:

```yaml
---
context_zen:
  version: "0.1"
  continuation: true
  enabled: true
---
```

`continuation` identifies the artifact as part of a Context Zen continuation. `enabled` says whether monitoring should remain active in the receiving context.

<ResearchBreakout mode="wide">
  <ContextZenContinuationLineageVisual />
</ResearchBreakout>

This also keeps manual checkpoints separate from monitoring. A user can request:

```text
context zen handoff
```

even when monitoring is off. The artifact can still be a continuation while carrying `enabled: false`. Creating a checkpoint does not silently opt the user into monitoring.

A host does not need durable cross-chat state for this model to work; the handoff itself can carry the continuation state forward. If the host exposes clipboard access, Context Zen can copy the complete handoff automatically. Otherwise it returns one self-contained artifact for the user to copy.

It does not assume it can create or navigate to a new conversation on the user's behalf.

## Compile the Same State for a Receiver

For v0.1, the user chooses the target.

A manual request can be explicit:

```text
context zen handoff
context zen handoff for codex
context zen handoff for research
```

If no target is supplied, Context Zen produces the canonical general-purpose handoff. A target profile changes organization and emphasis rather than the underlying state.

<ResearchBreakout mode="wide">
  <ContextZenTargetProfilesVisual />
</ResearchBreakout>

A coding profile can foreground repository state, branch, current files, architecture decisions, tests, failures, and the next implementation step.

A research profile can foreground the research question, established findings, sources, assumptions, unresolved questions, and the next investigation.

The specification says targeting should not change or omit state that could materially alter continuation. That is an architectural requirement, not a demonstrated guarantee that every generated handoff will satisfy it perfectly.

I think of this as closer to **context recompilation** than ordinary summarization: preserve the authoritative state, then represent it for the environment that will consume it next. That is useful framing, but it is not yet an experimentally established category.

## Test Distillation Against Compression

The repository defines opt-in activation, continuation-lineage propagation, qualitative context-health assessment, manual handoff, distillation rules, a canonical handoff format, clipboard behavior where supported, and coding and research target profiles.

What it does **not** provide is evidence that a Context Zen handoff improves continuation.

A useful experiment needs three conditions:

<ResearchBreakout mode="wide">
  <ContextZenExperimentBaselineVisual />
</ResearchBreakout>

The ordinary-summary arm matters. Comparing only a full transcript with a distilled handoff would mix two possible effects: making the context shorter and reconstructing authoritative working state. A conventional summary gives the experiment a compression baseline.

Candidate measures could include missed active constraints, accidental revival of rejected decisions, repeated questions, user corrections, task completion quality, token use, latency, and target-specific success.

Different work may benefit from different amounts of raw history. Rejected decisions may prove unusually important to preserve. The experiment has not established the answer.

The idea of **state entropy** may eventually help connect qualitative context health to something more testable: what share of retained context is superseded, conflicting, abandoned, or no longer actionable?

I am using *state entropy* as a working architectural metaphor, not a validated quantitative measure. It belongs in the experiment as a hypothesis to investigate, not as a result.

## The Complement to Retrieval

A lot of context engineering is naturally focused on retrieval:

> How do we get more of the right information into the model?

Context Zen explores the complementary operation:

> **When should we deliberately remove information from active context?**

Retrieval brings relevant state in. Distillation decides what deserves to stay. Handoff creates a clean boundary at which to reset the rest.

The broader hypothesis is not that less context is always better. It is that chronological completeness and continuation quality are different objectives.

> **A healthy agent context is not the one that remembers the most. It is the one that preserves the right state with the least ambiguity.**
