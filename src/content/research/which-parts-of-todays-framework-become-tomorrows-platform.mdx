## The Question I Started With

I started this investigation with a stronger assumption than the evidence supported: **were standards bodies moving enough framework responsibilities into the platform that much of the framework layer could eventually disappear?**

The evidence pushed me toward a different question:

> **If more framework-era ideas become native primitives, how will the responsibilities of the browser platform, frameworks, compilers, libraries, servers, and application code be redistributed?**

That revised question changes the shape of the investigation. Instead of asking whether frameworks vanish, I am looking at where responsibilities are moving.

---

## A Working Boundary Between Platform and Framework

The web platform tends to absorb **capabilities whose semantics have become broadly understood and useful across many architectures**. Frameworks can then coordinate those capabilities and impose application policy above them.

The movement to watch is between platform primitives and framework coordination. If native primitives become more capable, frameworks may own less low-level machinery while still owning higher-level composition, policy, and application architecture.

## Signals: A Primitive Below Framework Policy

The [TC39 Signals proposal](https://github.com/tc39/proposal-signals) is revealing because its stated goal is narrower than a native framework-level reactivity system. As of September 17, 2026, Signals remains a [Stage 1 TC39 proposal](https://github.com/tc39/proposals/blob/main/stage-1-proposals.md), focused on a common underlying signal graph and auto-tracking model that frameworks could build on top of rather than a complete developer-facing reactive runtime.

A standardized reactive primitive could reduce the need for every framework to implement the same low-level dependency graph semantics independently. It could improve interoperability between reactive libraries, give tooling a shared model to inspect, and potentially support future HTML or DOM work.

But the proposal deliberately leaves effect scheduling, ownership, disposal, batching policy, and rendering coordination above the primitive. That separation matters because it creates the possibility of **shared reactive infrastructure without requiring frameworks to share the same rendering or scheduling model**:

## Web Components: Standard Components, Not Standardized Applications

[Custom Elements](https://html.spec.whatwg.org/multipage/custom-elements.html), Shadow DOM, templates, slots, and related Web Components work give the web a standardized component substrate.

That is significant. A component can have a browser-recognized identity, lifecycle, encapsulated tree, styling boundaries, and reusable markup without belonging to a particular application framework.

But a component model is not an application architecture. Web Components do not determine application state and scheduling, routing and data coordination, server/client execution, compilation strategy, or the organizational conventions used to structure a large codebase.

That was a key correction to my original mental model: **standard components establish portable component identity without defining how an application should be coordinated around those components.**

## Additional Signals From the Platform

Looking across TC39, WHATWG, CSSWG, WICG, the Web Components community, and Open UI, I do not see one unified roadmap whose stated destination is "make frameworks unnecessary." I see multiple efforts moving different mechanisms into durable platform contracts.

**User-journey primitives.** The [Navigation API](https://html.spec.whatwg.org/multipage/nav-history-apis.html#the-navigation-api) provides a modern application-oriented model for navigation and session history, while the [CSS View Transitions specification](https://drafts.csswg.org/css-view-transitions-2/) moves visual state-transition mechanics into browser-coordinated primitives. Routers and frameworks can build policy around those mechanisms rather than reconstructing all of them from lower-level browser APIs.

**DOM update primitives.** Proposals such as [DOM Parts](https://github.com/WICG/webcomponents/blob/gh-pages/proposals/DOM-Parts.md) explore efficient handles to mutable positions in the DOM, while earlier [template-instantiation work](https://github.com/WICG/webcomponents/blob/gh-pages/proposals/Template-Instantiation.md) explored more reusable templating infrastructure. These remain exploratory, but they show continued interest in moving DOM-update machinery beneath framework-specific template systems.

**Control primitives.** [Open UI](https://open-ui.org/) studies common controls, component anatomy, state, behavior, styling, and accessibility patterns already repeated across frameworks and design systems, then considers which pieces may belong in HTML, CSS, JavaScript, ARIA, or related platform work.

## What Frameworks Still Own: Coordination and Policy

These platform efforts matter because they move mechanisms downward. Frameworks remain useful partly because they can make opinionated decisions that standards bodies often should not make for every application.

Those decisions cluster into three kinds of policy:

- **Execution policy** — when work is scheduled, how updates batch, how rendering composes, and how pending or error states propagate.
- **Application architecture** — how routing, data loading, nested layouts, and server/client execution fit together.
- **Developer contract** — which templating model, compiler strategy, optimization pipeline, conventions, and developer experience define how a team builds the application.

Those are not all missing standards. Some are **policy choices**.

A browser primitive must remain general enough to support many application models. A framework can deliberately narrow the design space and provide a coherent way to compose those primitives into an application.

## The Likely Recomposition

Frontend responsibilities repeatedly move between browser, runtime, compiler, server, and application layers as lower-level capabilities mature. When repeated framework behavior becomes legible enough to standardize, frameworks can reorganize around the new primitive:

</ResearchBreakout>

If that pattern continues, the practical consequences could be more specific than simply "thinner frameworks":

- reactive libraries could share a standardized dependency graph while keeping their own scheduling, effect, and rendering policies
- routers could delegate more navigation and session-history mechanics to the Navigation API while concentrating on route matching, data loading, and layout conventions
- transition systems could coordinate application state around native View Transitions instead of owning the full visual-transition mechanism
- component systems, design systems, and compilers could increasingly target shared platform primitives while differentiating through composition, optimization, server integration, and developer experience

In that version of the stack, framework differentiation shifts upward: less value comes from privately reimplementing common substrate, and more comes from how effectively the framework coordinates the platform into an application model.

## Research Questions From Here

This draft leaves four questions I want to keep pushing on:

1. **What is the minimum useful framework if components, reactivity, navigation, transitions, and more templating infrastructure become native?**
2. **Which current framework responsibilities are truly missing platform primitives, and which are intentionally application-level policy?**
3. **Do compilers and meta-frameworks become more important as UI runtimes become thinner?**
4. **What does a serious application built deliberately around the platform-first version of this architecture look like?**

The last question is the most concrete next step: **test this boundary model against a serious application built deliberately around platform primitives, then document which responsibilities still demand framework-level coordination.**
