## The Question I Started With

I started this investigation with a stronger assumption than the evidence supported: **were standards bodies moving enough framework responsibilities into the platform that much of the framework layer could eventually disappear?**

The evidence pushed me toward a different question:

> **If more framework-era ideas become native primitives, how will the responsibilities of the browser platform, frameworks, compilers, libraries, servers, and application code be redistributed?**

That revised question changes the shape of the investigation. Instead of asking whether frameworks vanish, I am looking at where responsibilities are moving.

---

## A Working Boundary Between Platform and Framework

The web platform tends to absorb **capabilities whose semantics have become broadly understood and useful across many architectures**. Frameworks can then coordinate those capabilities and impose application policy above them.

That produces a working boundary:

The movement to watch is between platform primitives and framework coordination. If native primitives become more capable, frameworks may own less low-level machinery while still owning higher-level composition, policy, and application architecture.

## Signals: A Primitive Below Framework Policy

The [TC39 Signals proposal](https://github.com/tc39/proposal-signals) is revealing because its stated goal is narrower than a native framework-level reactivity system. As of September 17, 2026, Signals remains a [Stage 1 TC39 proposal](https://github.com/tc39/proposals/blob/main/stage-1-proposals.md), focused on a common underlying signal graph and auto-tracking model that frameworks could build on top of rather than a complete developer-facing reactive runtime.

A standardized reactive primitive could reduce the need for every framework to implement the same low-level dependency graph semantics independently. It could improve interoperability between reactive libraries, give tooling a shared model to inspect, and potentially support future HTML or DOM work.

But the proposal deliberately leaves effect scheduling, ownership, disposal, batching policy, and rendering coordination above the primitive. Its boundaries are what make it useful evidence for the larger model:

## Web Components: Standard Components, Not Standardized Applications

[Custom Elements](https://html.spec.whatwg.org/multipage/custom-elements.html), Shadow DOM, templates, slots, and related Web Components work give the web a standardized component substrate.

That is significant. A component can have a browser-recognized identity, lifecycle, encapsulated tree, styling boundaries, and reusable markup without belonging to a particular application framework.

But a component model is not an application architecture. Web Components do not determine application state and scheduling, routing and data coordination, server/client execution, compilation strategy, or the organizational conventions used to structure a large codebase.

That was a key correction to my original mental model: **standard components remove one reason for framework ownership without standardizing the rest of application architecture.**

## Additional Signals From the Platform

Looking across TC39, WHATWG, CSSWG, WICG, the Web Components community, and Open UI, I do not see one unified roadmap whose stated destination is "make frameworks unnecessary."

Instead, multiple efforts are moving different mechanisms into durable platform contracts.

### Navigation mechanics

The [Navigation API](https://html.spec.whatwg.org/multipage/nav-history-apis.html#the-navigation-api) provides a modern application-oriented model for navigation and session history, including interception of same-document navigations.

That moves more navigation mechanics into the platform without deciding an application's routing conventions, nested layouts, or data-loading model.

### Transition mechanics

The [CSS View Transitions specification](https://drafts.csswg.org/css-view-transitions-2/) moves visual state-transition mechanics into a browser-coordinated primitive.

The browser can provide the mechanism while applications and frameworks still decide when a transition is appropriate and how it participates in application state.

### Dynamic DOM and templating

The Web Components community continues to explore proposals such as [DOM Parts](https://github.com/WICG/webcomponents/blob/gh-pages/proposals/DOM-Parts.md), intended to give code efficient handles to mutable positions in the DOM.

There is also a long history of [template-instantiation exploration](https://github.com/WICG/webcomponents/blob/gh-pages/proposals/Template-Instantiation.md). These remain exploratory proposals, not evidence that native framework-style templating is settled, but they show continued interest in moving more reusable DOM machinery beneath framework-specific template systems.

### Common UI controls and patterns

[Open UI](https://open-ui.org/) studies common controls, component anatomy, state, behavior, styling, and accessibility patterns that are repeatedly reinvented by frameworks and design-system libraries.

Its charter is especially interesting because it examines patterns already common in third-party systems and considers which pieces may belong in HTML, CSS, JavaScript, ARIA, or related platform work.

## What Frameworks Still Own: Coordination and Policy

These platform efforts matter because they move mechanisms downward. Frameworks remain useful partly because they can make opinionated decisions that standards bodies often should not make for every application.

A framework can decide:

- when work should be scheduled
- how updates should batch
- how rendering should compose
- whether templates use JSX, HTML-like syntax, compiler directives, or plain JavaScript
- how server and client execution divide responsibility
- how data loaders participate in routing
- how layouts nest
- how errors and pending states propagate
- how modules are compiled and optimized
- which conventions make a large team productive

Those are not all missing standards. Some are **policy choices**.

A browser primitive must remain general enough to support many application models. A framework can deliberately narrow the design space and provide a coherent way to compose those primitives into an application.

---

## The Likely Recomposition

Frontend history repeatedly decomposes responsibilities and then recomposes them at a different layer. Browsers gain capabilities, build tools absorb transforms, servers re-enter rendering, compilers move work out of the runtime, and frameworks reorganize around the new boundaries.

Repeated framework behavior can become legible enough to standardize at a lower layer, after which frameworks build new coordination and conventions above it:

My working hypothesis is that frontend architecture will become increasingly layered around a more capable shared platform, while frameworks compete less on proprietary implementations of low-level primitives and more on how those primitives are composed.

That could mean:

- more reactive and component code that is portable across rendering systems
- less framework-specific machinery where the browser can provide the primitive directly
- more framework differentiation around compilers, routing, server execution, data flow, and application conventions
- better interoperability between libraries because lower-level contracts are shared

The point is not that the ecosystem converges on one stack. The point is that **the boundary between platform and framework remains an active architectural design space**.

---

## Research Questions From Here

This draft leaves four questions I want to keep pushing on:

1. **What is the minimum useful framework if components, reactivity, navigation, transitions, and more templating infrastructure become native?**
2. **Which current framework responsibilities are truly missing platform primitives, and which are intentionally application-level policy?**
3. **Do compilers and meta-frameworks become more important as UI runtimes become thinner?**
4. **What does a serious application built deliberately around the platform-first version of this architecture look like?**

The last question is the one that may eventually turn this research into an implementation project.
