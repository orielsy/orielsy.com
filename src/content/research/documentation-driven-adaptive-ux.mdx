## The Documentation / Interface Disconnect

Enterprise software usually treats product knowledge and product behavior as separate systems. The application knows its state. Validation knows which values are required. Documentation explains concepts, release notes describe version changes, and implementation guides tell users how to make a choice. Those sources often live outside the interface that needs them.

The familiar result is an external detour: a user reaches a configuration field, encounters uncertainty, leaves the application, searches documentation, interprets what they find, and then returns to the original task.

<p className="paper-pullquote">Move the knowledge, not the user.</p>

<DocumentationDrivenAdaptiveVisual />

The opportunity is not simply to move documentation into a tooltip. A static tooltip gives every user the same explanation. A context-aware interface can determine whether a note applies to the current version, whether the user needs conceptual help, and whether the available evidence supports an action.

The reference experiment makes this concrete at one required Data Connection field. A standard form and an adaptive form receive the same version, simulated user familiarity, compatible options, and validation rule. The adaptive form can explain a missing choice, vary authored guidance, or offer the sole compatible connection for the user to accept; it cannot choose among several. The working comparison appears below, after the decision boundaries that explain it.

## Start with Application Truth

The first architectural rule is simple: the application remains authoritative. Documentation can explain a rule, but it should not redefine it. Product knowledge can enrich the experience, but deterministic business logic should remain deterministic.

Taking that rule seriously separates the experiment into seven concerns. They fall into three groups, and the groups are also the order in which a decision is made: the application establishes what is true, authored knowledge is selected against that truth, and only then does the interface decide how strongly to respond and how to show it. Every concern reads from the groups before it; none writes back. No step requires inference.

<Phase1DeterministicPipelineVisual figureNumber="01" />

Keeping these responsibilities visible gives later AI capabilities a clean place to enter without asking them to replace validation, compatibility rules, or product state.

## Why Deterministic First?

A required field, a version-specific note, or a single compatible option is already knowable from application state and authored rules. Starting there lets Phase 1 test the separation between product truth, relevant guidance, and permission to intervene without introducing inference as another source of uncertainty.

## Structured Product Knowledge

The reference implementation does not ingest real documentation yet. Instead, it models small authored knowledge fragments that approximate what a future ingestion or authoring pipeline could produce.

The fragments include a basic Data Connection summary, required-field help, a beginner-oriented concept explanation, version 4.2 guidance, and configuration-selection guidance. Each carries applicability information such as audience, version, and state conditions, plus provenance identifying whether it represents documentation or a release note.

Version-specific knowledge applies only when the product is at least version 4.2 and the Data Connection is missing. Beginner help applies only to a new user in the same missing-connection state.

<p className="paper-pullquote">Context selection, not context accumulation.</p>

The goal is not to dump all related documentation into the interface. First narrow the available knowledge according to deterministic facts, then decide how much of it deserves to become interface behavior.

## Knowledge Applicability Is Not Response Policy

Knowing something applies does not automatically determine what the interface should do with it.

**Knowledge applicability** asks whether authored information matches the current product state, version, and audience. **Response policy** asks how strongly the interface should intervene given that state, the validation result, available knowledge, and certainty of the evidence.

A version note can be relevant without deserving a modal. A beginner explanation can apply without changing validation. A configuration guide can apply while the interface still refuses to choose among several valid options.

This separation becomes especially important if semantic retrieval is added later. Retrieval can rank or discover relevant knowledge while response policy still decides whether the result becomes help text, a highlight, a suggestion, or an action.

## UI Authority Should Follow Evidence

The more deterministic the evidence, the more strongly the interface may act. The progression can move from no intervention through expanded description, contextual help, current-state explanation, highlighting, and a suggested next action to preconfiguring a safe value. Phase 1 never performs an autonomous destructive action.

The critical boundary is between guidance and choice.

If several Data Connections are compatible, the system can explain the requirement and guide the user toward the field, but it does not know which connection matches the user’s intent. It must not guess.

If exactly one compatible Data Connection exists, the evidence changes. The interface can safely offer that value as a user-accepted action because no competing valid candidate remains.

The deterministic experiment suggests that inference should resolve ambiguity rather than invent application truth. That is a much smaller and safer responsibility than asking a model to infer the entire interaction model at once.

## Limitations of the Current Experiment

Phase 1 is not a production adaptive-UX platform. Its product knowledge is authored fixture data, its compatibility scenarios are fixed demo data, and user familiarity is a simulation control rather than an inferred or persisted profile.

<Phase1LimitationsVisual />

The experiment also does not answer how knowledge fragments are reviewed, stale release guidance is retired, conflicting sources are reconciled, or intervention quality is measured. Those are not omissions hidden behind the demo; they are deliberately outside the Phase 1 question.

## Where AI Could Enter Later

The deterministic architecture gives future inference explicit seams. Optional inference could sit after deterministic filtering and before evidence reconciliation and response policy.

<div className="paper-future-capabilities">
  <article><h3>Natural-language intent resolution</h3><p>Map a user’s language to the relevant product concept, while the deterministic resolver still checks current state before responding.</p></article>
  <article><h3>Semantic product-knowledge retrieval</h3><p>Rank knowledge after filters such as version, environment, permissions, or feature availability have reduced the candidate set.</p></article>
  <article><h3>Explanation adaptation</h3><p>Rewrite or compress an already-authorized explanation while preserving its facts and action boundary.</p></article>
</div>

Where such inference would run is a separate, unevaluated question. Browser-local processing could keep some application context on the device; routing between browser, local service, and remote model would be a deployment decision, not another interface capability.

## From Documentation Portal to Product Capability

The broader direction is not to eliminate documentation. Long-form documentation remains necessary for learning, implementation, troubleshooting, and reference. The opportunity is to stop treating it as useful only after the user leaves the product to search for it.

Some product knowledge can be structured so the application understands what concept it describes, which state makes it relevant, which versions it applies to, which audience needs it, where it came from, and what level of action it can safely support.

At that point, documentation is no longer only a destination. It becomes one input into interface behavior. The strongest version is not an interface that constantly talks: it becomes quieter when context is obvious, more explanatory when uncertainty is predictable, and more helpful only when the available evidence justifies it.

<p className="paper-pullquote">How adaptive can an enterprise interface become before AI is necessary?</p>

In this reference implementation, far enough to tailor guidance and offer an unambiguous choice without inference. Whether that improves the experience—and where inference would add value—remains to be tested.
