## The Documentation / Interface Disconnect

Enterprise products accumulate operational knowledge across documentation, release notes, runbooks, support articles, and configuration guidance. Their interfaces often expose only the raw controls.

A field may know that a value is missing. The application may know the current version and valid options. Documentation may explain why the field matters. The user is still expected to assemble that context manually.

<ResearchBreakout mode="publication">
  <DocumentationDrivenAdaptiveVisual />
</ResearchBreakout>

The opportunity is to **select and surface authored product knowledge according to current application state**, rather than make every user leave the product or receive the same static explanation.

That does not mean documentation becomes application logic. The more interesting architectural question is how knowledge can reach the task **without acquiring authority over product truth or user intent**.

## Phase 1 as a Deterministic Baseline

Phase 1 narrows the experiment to one product field: **Data Connection**.

The reference application varies three controlled inputs: user familiarity, product version, and whether one or several compatible Data Connections remain. Two independently operable forms then receive that same scenario and the same required-field rule.

The [Adaptive Enterprise UI Lab](/projects/adaptive-enterprise-ui-lab) is the working artifact for that comparison. The project page owns the complete interaction: scenario controls, validation, the explicit one-option offer, source-labelled guidance, and the inspectable decision trace.

This paper uses that artifact as evidence rather than embedding a second copy of the lab. Its job is to extract the architecture and limits that may transfer beyond this one field.

## Deriving the Architecture

**The application remains authoritative.**

Documentation can explain a rule, but it should not redefine it. Known constraints belong in testable code or configuration; future inference can help with ambiguity without becoming the source of product truth.

The experiment separates seven concerns:

<ol className="paper-concern-grid">
  <li><strong>Domain state</strong><span>what the user has selected.</span></li>
  <li><strong>Runtime and user context</strong><span>product version, user familiarity, and available compatible options.</span></li>
  <li><strong>Validation</strong><span>deterministic application requirements.</span></li>
  <li><strong>Product knowledge</strong><span>authored explanatory material and configuration guidance.</span></li>
  <li><strong>Knowledge applicability</strong><span>whether a specific knowledge item applies to the current state.</span></li>
  <li><strong>Response policy</strong><span>how strongly the interface should intervene given the available evidence.</span></li>
  <li><strong>Rendering</strong><span>how those structured responses appear in the UI.</span></li>
</ol>

Starting deterministically exposes those boundaries and creates a baseline against which later inference can be evaluated.

## Structured Product Knowledge

Phase 1 uses small authored knowledge fragments rather than ingested documentation: a Data Connection summary, required-field help, beginner guidance, version 4.2 guidance, and configuration-selection guidance.

Each fragment carries applicability information such as audience, version, and state conditions, plus simple provenance metadata.

That distinction matters. Phase 1 demonstrates **authored fixture knowledge with explicit conditions**. It does not demonstrate document ingestion, semantic retrieval, stale-content governance, source conflict resolution, or a production publishing workflow for product knowledge.

The design goal is **context selection, not context accumulation**: narrow the available knowledge using deterministic facts before deciding whether any of it should affect the interface.

## Knowledge Applicability Is Not Response Policy

Knowing something applies does not determine what the interface should do with it.

Knowledge applicability asks:

> Does this authored information match the current product state, version, and audience?

Response policy asks:

> Given the application state, validation result, available knowledge, and certainty of the evidence, how strongly should the UI intervene?

Keeping those decisions separate prevents the knowledge layer from becoming an accidental UI controller. A matching release note can add context; it cannot select a Data Connection or redefine what counts as valid.

## Evidence Bounds Interface Authority

Phase 1 uses a simple architectural preference: **more deterministic evidence can justify stronger help, but ambiguity still limits authority.**

The controlled scenarios make that boundary concrete:

<ResearchBreakout mode="publication">
  <AdaptiveUxScenarioEvidenceVisual />
</ResearchBreakout>

The one-versus-several distinction is the clearest example. Several compatible values leave user intent unresolved, so explanation and guidance are appropriate but selection is not. Exactly one compatible value supports an explicit offer, while the user still accepts the preconfiguration rather than the interface silently changing state.

Familiarity and version demonstrate a different kind of adaptation: they change which explanation is applicable without changing the validation rule. A valid selection demonstrates the inverse boundary: related knowledge may still exist, but the missing-field intervention should disappear once the state no longer requires it.

Taken together, Phase 1 supports four narrower conclusions: product knowledge can participate in UI behavior without owning business logic; useful adaptation can exist before inference; certainty is a practical control on interface authority; and structured response policy can keep the renderer from rediscovering those decisions independently.

Those are architectural observations from this controlled reference implementation, not measured claims about user performance or intervention quality.

## Limitations of the Current Experiment

Phase 1 is a reference experiment, not a production adaptive-UX platform.

<ResearchBreakout mode="publication">
  <Phase1LimitationsVisual />
</ResearchBreakout>

Product knowledge is fixture data, compatibility scenarios are fixed, and user familiarity is a simulation control.

The experiment also leaves production governance unanswered: review, stale guidance, conflicting sources, measurement of intervention quality, and the operational ownership of product knowledge.

## Where AI Could Enter Later

The deterministic pipeline leaves an explicit seam for optional inference after context filtering and before response policy:

<ResearchBreakout mode="publication">
  <WhereAiCouldEnterLaterVisual />
</ResearchBreakout>

Potential later uses of that seam remain deliberately narrower than product truth or business policy:

- **Intent resolution:** map freeform language to a known product concept while deterministic state remains authoritative.
- **Semantic retrieval:** rank product knowledge after version, environment, permissions, or feature filters reduce the candidate set.
- **Explanation adaptation:** rewrite or compress an already-authorized explanation without changing its facts or action boundary.
- **Browser-local inference:** run narrow classification or ranking locally when the model and hardware are sufficient.
- **Runtime routing:** eventually decide whether an inference task belongs in the browser, a local service, or a remote model.

These are future capabilities, not Phase 1 behavior. Any inferred result would still need to be reconciled against application state and approved knowledge before response policy or the UI acts on it. No runtime placement strategy has been evaluated or deployed by this experiment.

## From Documentation to Product Capability

Long-form documentation remains necessary. But when product knowledge carries applicability, provenance, and action boundaries, it can also become an input to interface behavior instead of only a destination outside the product.

Phase 1 shows that useful adaptation does not require inference. Deterministic architecture does not eliminate AI; it defines its job: **help where ambiguity remains without becoming the source of product truth.**
