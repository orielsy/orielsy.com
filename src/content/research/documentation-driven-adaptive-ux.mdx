## The Documentation / Interface Disconnect

Enterprise products accumulate operational knowledge across documentation, release notes, runbooks, support articles, and configuration guidance. Their interfaces often expose only the raw controls.

A field may know that a value is missing. The application may know the current version and valid options. Documentation may explain why the field matters. The user is still expected to assemble that context manually.

The opportunity is to **select and surface authored product knowledge according to current application state**, rather than make every user leave the product or receive the same static explanation.

<DocumentationDrivenAdaptiveVisual />

This is a conceptual comparison of where product knowledge meets the task, not evidence that the adaptive path produces better outcomes. The companion project’s working lab provides the actual Phase 1 behavior.

## Phase 1 Experiment: One Field, Two Interface Policies

Phase 1 narrows the experiment to one product field: **Data Connection**.

The shared controls vary three pieces of context:

<ul className="paper-scenario-grid">
  <li><strong>User familiarity</strong>New or Experienced</li>
  <li><strong>Product version</strong>4.1 or 4.2</li>
  <li><strong>Compatible Data Connections</strong>One or Several</li>
</ul>

Both interfaces receive the same scenario and application truth.

### Standard UI

The Standard UI exposes the required field and ordinary validation. If the user continues without a Data Connection, it reports the missing value.

This is a normal enterprise form pattern, not a straw man: expose configuration, validate input, and rely on documentation or prior knowledge when interpretation is required.

### Adaptive UI

The Adaptive UI keeps the same field and validation rule, then adds authored product knowledge and response policy. It can surface conceptual help, version-specific guidance, and the relevant control while varying its permitted action according to the available evidence.

## Deriving the Architecture

**The application remains authoritative.**

Documentation can explain a rule, but it should not redefine it. Known constraints belong in testable code or configuration; future inference can help with ambiguity without becoming the source of product truth.

Taking that rule seriously separates the experiment into seven concerns. They fall into three groups, and those groups are also the order in which a decision is made: the application establishes what is true, authored knowledge is selected against that truth, and only then does the interface decide how strongly to respond and how to show it. Every concern reads from the groups before it; none writes back. No step requires inference.

<Phase1DeterministicPipelineVisual figureNumber="01" />

That separation creates a deterministic baseline for later inference without asking it to replace validation, compatibility rules, or product state.

## Structured Product Knowledge

Phase 1 uses small authored knowledge fragments rather than ingested documentation: a Data Connection summary, required-field help, beginner guidance, version 4.2 guidance, and configuration-selection guidance.

Each fragment carries applicability information such as audience, version, and state conditions, plus simple provenance metadata.

The design goal is **context selection, not context accumulation**: narrow the available knowledge using deterministic facts before deciding whether any of it should affect the interface.

## Knowledge Applicability Is Not Response Policy

Knowing something applies does not determine what the interface should do with it.

Knowledge applicability asks:

> Does this authored information match the current product state, version, and audience?

Response policy asks:

> Given the application state, validation result, available knowledge, and certainty of the evidence, how strongly should the UI intervene?

<ApplicabilityVsPolicyVisual figureNumber="02" />

Keeping those decisions separate prevents the knowledge layer from becoming an accidental UI controller.

## UI Authority Should Follow Evidence

The more deterministic the evidence, the more strongly the interface may act. The progression can move from no intervention through expanded description, contextual help, current-state explanation, highlighting, and a suggested next action to preconfiguring a safe value. Phase 1 never performs an autonomous destructive action.

The critical boundary is between guidance and choice.

If several Data Connections are compatible, the system can explain the requirement and guide the user toward the field, but it does not know which connection matches the user’s intent. It must not guess.

If exactly one compatible Data Connection exists, the evidence changes. The interface can safely offer that value as a user-accepted action because no competing valid candidate remains.

## Limitations of the Current Experiment

Phase 1 is a reference experiment, not a production adaptive-UX platform. It excludes:

<Phase1LimitationsVisual />

Product knowledge is fixture data, compatibility scenarios are fixed, and user familiarity is a simulation control.

The experiment also leaves production governance unanswered: review, stale guidance, conflicting sources, and measurement of intervention quality.

## Where AI Could Enter Later

The deterministic pipeline leaves an explicit seam for optional inference after context filtering and before response policy:

<WhereAiCouldEnterLaterVisual figureNumber="04" />

Potential later uses of that seam remain deliberately narrower than product truth or business policy:

- **Intent resolution:** map freeform language to a known product concept while deterministic state remains authoritative.
- **Semantic retrieval:** rank product knowledge after version, environment, permissions, or feature filters reduce the candidate set.
- **Explanation adaptation:** rewrite or compress an already-authorized explanation without changing its facts or action boundary.
- **Browser-local inference:** run narrow classification or ranking locally when the model and hardware are sufficient.
- **Runtime routing:** eventually decide whether an inference task belongs in the browser, a local service, or a remote model.

These are future capabilities, not Phase 1 behavior. Any inferred result would still need to be reconciled against application state and approved knowledge before response policy or the UI acts on it.

## From Documentation to Product Capability

Long-form documentation remains necessary. But when product knowledge carries applicability, provenance, and action boundaries, it can also become an input to interface behavior instead of only a destination outside the product.

Phase 1 shows that useful adaptation does not require inference. Deterministic architecture does not eliminate AI; it defines its job: **help where ambiguity remains without becoming the source of product truth.**
