## Scope Boundary: What the UI Does vs. Where It Runs

[AI as a UI Capability, Not Just a Chatbot](/research/ai-as-ui-capability-not-chatbot) explores **what kinds of intelligent behavior belong directly inside an interface**. This draft is intentionally narrower: it begins after such a capability has been requested and asks **how and where that work should execute**.

Concepts such as semantic filtering, structured extraction, intent interpretation, contextual transformation, and adaptive guidance belong primarily to the interface-capability discussion. This article owns the execution layer beneath them: browser-local inference, machine-local runtimes, server or edge execution, cloud fallback, capability detection, privacy, latency, availability, device constraints, cost, and enterprise governance.

## The Execution Problem: One Runtime Tier for Every Capability

Many AI-enhanced interfaces begin with a single execution assumption: send the request to a remote model endpoint. That can be entirely appropriate, but it is not the only possible architecture.

Different interface capabilities may eventually have different execution constraints. Some may be candidates for browser-local inference, some may require a machine-local runtime, and others may belong on server, edge, or cloud infrastructure.

```text
Interface requests an AI capability
            |
            v
     [Capability Router]
            |
            |--> [Browser-Local WebGPU / WebLLM]   (candidate tier)
            |--> [Machine-Local Runtime]            (candidate tier)
            |--> [Server / Edge]                    (candidate tier)
            '--> [Cloud Model Endpoint]             (candidate tier)
```

The routing problem is not simply "local is better" or "cloud is better." A useful runtime would need to reconcile the needs of the task with what the current environment can actually support.

## Architectural Questions for Tiered Inference

### 1. Runtime Capability Detection

A future runtime could inspect signals that help determine whether a local execution path is even viable, including:

- **WebGPU availability and adapter capabilities** exposed by the browser.
- **CPU/WASM capabilities** relevant to non-GPU local execution.
- **Memory and device constraints** that may make a model or task unsuitable for a client tier.
- **Runtime availability** for machine-local services where a desktop companion is part of the product architecture.

These signals indicate capability, not guaranteed performance. Performance and compatibility conclusions require measured implementation.

### 2. Task Requirements

Execution choice should also be constrained by what the requested capability needs. Candidate dimensions include:

- privacy and data-residency requirements
- acceptable interaction latency
- model or runtime availability
- offline or degraded-network requirements
- expected computation cost
- device capability
- enterprise policy and governance

A conceptual routing contract might look like this:

```typescript
interface InferenceRequest<TInput, TOutput> {
  id: string;
  requiresLocalDataHandling: boolean;
  preferredLatencyClass: 'interactive' | 'background';
  input: TInput;
  executeWith(runtime: InferenceRuntime): Promise<TOutput>;
}

interface InferenceRuntime {
  kind: 'browser-local' | 'machine-local' | 'server' | 'cloud';
  available: boolean;
}
```

This is a design sketch, not a current implementation.

### 3. Fallback and Availability

An adaptive runtime would also need explicit fallback behavior. If a browser-local model cannot load, if a device lacks the required capability, or if local execution conflicts with product policy, the interface needs a defined alternative rather than silently failing or pretending every tier is interchangeable.

Fallback itself has product consequences: the UI may need to communicate that a capability is unavailable, delayed, privacy-sensitive, or executing through a different tier.

### 4. Governance and Cost

Execution architecture is also a governance boundary. Browser-local, machine-local, and remote runtimes may differ in data exposure, operational cost, observability, update control, and compliance requirements.

Those tradeoffs should be evaluated per capability and environment rather than inferred from the runtime label alone.

## Browser-Local Inference as a Future Deep Dive

WebGPU and runtimes such as WebLLM make the browser a plausible future execution tier for some workloads. That deserves its own measured experiment rather than speculative benchmark claims inside this broader architecture draft.

A separate unpublished experiment, **Browser-Local Inference as a UI Runtime Capability**, will hold that narrower work once an implementation exists. It is subordinate to this runtime architecture rather than a replacement for it.

## Summary & Next Explorations

Adaptive AI Runtime is the **how / where** layer beneath intelligent interface capabilities. Its open question is whether a product can choose among browser-local, machine-local, server, edge, and cloud execution tiers without confusing capability selection with application truth or UI behavior.

Future work should remain evidence-driven. Browser compatibility, model size, memory use, latency, and routing quality should be documented only after they are measured in a real implementation.
