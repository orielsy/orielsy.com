Over the last several months, I have been exploring what initially looked like separate problems.

How can coding agents retain important project decisions across sessions? How should a repository select only the context relevant to the task at hand? Can product documentation participate in interface behavior without replacing deterministic application state? And if AI can generate interface components more cheaply, what becomes the more valuable architectural layer?

Each question produced its own investigation: durable project memory, task-aware context selection, documentation-driven adaptive UX. Each answered something on its own. But the more of them I work through, the more they appear to be manifestations of one deeper architectural question.

Software has long had explicit places for behavior, state, and structure. Code expresses implemented behavior. Databases and application state preserve current facts. Schemas define valid structure and contracts. The meaning surrounding those systems — intent, relevance, explanation, policy rationale, composition — is often more fragmented.

AI changes what software can do with that layer. Not because a language model should be allowed to improvise product behavior, but because product knowledge that was once primarily written for people can increasingly become input to the systems that build and operate software.

That suggests a working thesis:

> **Context is becoming a first-class architectural primitive, and some interfaces may become derived views of structured product knowledge over a bounded capability system.**

The first half of that sentence is the pattern my earlier work has been circling. The second half is the new question:

> **If reliable capabilities already exist, how much of a product's final composition still needs to be encoded imperatively — and how much can instead be derived from state, policy, product knowledge, and context?**

---

## The Pattern I Kept Running Into

Each earlier investigation approached one edge of this question.

```text
Project Memory          → make project knowledge durable
Context Engineering     → select relevant durable knowledge
Documentation-Driven UX → apply knowledge against runtime context
Declarative Composition → ask whether knowledge can help assemble the experience
```

[From Prompts to Project Memory: Spec-Driven Development for Coding Agents](/research/specification-driven-ai-development) asked how specifications, decisions, and repository rules could become durable memory for coding agents — knowledge that survives the session that produced it.

My still-unpublished work on context engineering for software development asks the follow-up: once that knowledge is durable, how does an agent receive only the subset relevant to the current task?

[Documentation-Driven Adaptive UX](/research/documentation-driven-adaptive-ux) moved the same pattern to runtime: authored product knowledge participating in interface behavior while deterministic application state and validation remain authoritative for the concerns they own.

Those pieces remain distinct. This article is the synthesis, but its new claim is not the recap. It is the **composition layer** those investigations begin to expose.

---

## Software Has Clear Homes for Behavior, State, and Structure

Ask where a mature system's current behavior, state, or structural contracts live and there is usually a concrete answer.

Ask where its meaning lives — why this flow exists, who this surface is for, when a capability is appropriate, why an action is unavailable, what should be explained at this moment — and the answer is often distributed across product documents, tickets, UI copy, support material, source-code conditionals, release notes, and human memory.

The bottom half of that model is the research proposition.

Machine-readable product knowledge is not new. Rule engines, expert systems, configuration-driven products, model-driven systems, and knowledge graphs have long encoded forms of meaning and policy. What AI changes is the practical range of **structured and semi-structured human-authored knowledge** that software can interpret, connect, and use as context.

I am not arguing that every product needs a literal new database called `context`. I am asking whether meaning, intent, and composition deserve more explicit architectural ownership instead of remaining accidental byproducts of implementation.

---

## Context as Architecture

When I say context is becoming a first-class architectural primitive, I mean something more specific than “stuff in the prompt.”

**Durable.** Important context survives the interaction that produced it. Decisions, constraints, and product intent persist as versioned artifacts rather than evaporating with a conversation.

**Selectable.** Durability without selection is just a larger pile. The system needs the relevant subset of knowledge for the task at hand rather than every document every time.

**Applicable.** Knowledge has conditions. Guidance that is correct for one product state, version, role, or audience may be wrong for another. Applicability must be evaluated against explicit context rather than guessed.

**Composable.** This is the new question. Once knowledge is durable, selectable, and applicable, can it also participate in choosing and arranging trusted capabilities into a useful product surface?

The first three properties map naturally to the research that came before this article. The fourth is the step I want to investigate next.

A primitive earns its place when the architecture is deliberately organized around it — when systems know how to store it, select it, validate where it applies, and constrain how it may affect behavior.

## One Knowledge Architecture, Different Consumers

Development-time context and runtime product knowledge are not operationally the same thing.

A coding agent may consume specifications, ADRs, architecture rules, component contracts, and implementation context. A runtime interface may consume product semantics, applicability metadata, explanatory guidance, policy references, and current user or product context.

Those consumers have different lifecycles and failure modes. What they can share is a broader **knowledge architecture**: durable product intent represented explicitly enough that different systems can select the parts appropriate to their job.

The authority model has to remain concern-specific.

```text
Current facts            → application state
Current implementation   → code tells us what happens now
Intended behavior        → governing specification / policy may outrank defective code
Meaning and explanation  → product knowledge
Conflict                 → a defect to surface, not a silent winner-takes-all rule
```

That distinction matters to Spec-Driven Development. If a governing specification says a restriction must not be removed before identity verification and the implementation allows it anyway, the code does not become correct merely because it is executable.

Likewise, product knowledge may describe a policy or explain why it exists, but deterministic policy and application code must still enforce the consequential rule.

The useful principle is not “code wins.” It is:

> **Authority belongs to the artifact responsible for the concern.**

## From Generated Components to Capability Systems

The obvious AI-and-UI story is generation: models can produce components and page code increasingly quickly.

That matters, but as generation becomes cheaper, another part of the problem becomes comparatively more valuable: deciding **what should exist, for whom, under what conditions, and within what constraints**.

Suppose engineering has already built a trustworthy vocabulary of product capabilities:

- customer profile
- account status
- transaction history
- identity verification
- account restriction actions
- risk escalation
- data tables
- forms
- filters
- charts
- workflow actions

Each capability has real implementation behind it. Inputs and outputs are defined. Authorization exists. Validation exists. Side effects are bounded. Tests can verify the mechanics.

At that point, a different question becomes possible:

> **How much final product composition still has to be authored as imperative page orchestration?**

A product or domain author might describe an account-review task in the language of the product:

```text
Account Review

Purpose
Investigate a restricted customer account.

Relevant information
- customer identity
- restriction reason
- recent activity
- verification state

Available actions
- request identity verification
- remove the restriction after verification succeeds
- escalate to risk review

Guidance
Explain unavailable actions through their unmet prerequisites.
```

That artifact did not implement identity verification, authorization, transaction retrieval, or account mutation. Engineering already supplied those capabilities.

What it supplied was **intent, relevance, prerequisites, policy context, and composition guidance**.

If a knowledgeable domain author can describe a large portion of the desired experience without implementing its mechanics, then perhaps there is a meaningful boundary here: developers build reliable capabilities and constraints; product knowledge describes how those capabilities should participate in a task.

The limit is real. A requirement no existing capability satisfies still requires implementation. A composition layer assembles what is already trusted; it does not conjure missing behavior into existence.

## Where AI Actually Fits

AI is what makes this layer newly practical in more situations, but it is easy to assign it the wrong job.

The weak version is:

```text
prompt
→ model invents page
→ hope the page obeys the product
```

The stronger version is closer to:

```text
current state
+ trusted capabilities
+ selected product knowledge
+ deterministic policy
→ bounded interpretation / composition
→ validated interface
```

AI can help bridge semantic gaps:

- interpret natural-language intent
- map a task to known product concepts
- retrieve relevant product knowledge
- select candidate capabilities
- adapt explanation to current context
- propose a composition
- translate human-authored knowledge into a structured representation

But the architecture must distinguish **interpretation** from **authority**.

A model may infer that “Why can't I remove this restriction?” refers to identity-verification policy. It should not get to invent whether verification succeeded, whether the user is authorized, or whether an irreversible action actually occurred.

The more consequential the action, the more important that boundary becomes.

---

## Documentation Is an Authoring Surface, Not the Architecture

This distinction keeps the thesis from collapsing into “Markdown runs the product.”

Traditional docs-as-code generally means documentation receives software-engineering practices: version control, review, build pipelines, automated checks, and deployment.

The claim here is different.

Documentation can become a human-friendly authoring surface for **product knowledge**. That knowledge can then be normalized, structured, tagged with provenance, connected to schemas, constrained by policy, and made selectable by other systems.

The durable architecture is not necessarily Markdown.

It is the layer of meaning the Markdown represents.

That also keeps documentation from being handed responsibilities it should not own. Product knowledge can describe intent, semantics, applicability, prerequisites, explanation, composition guidance, and the rationale behind a policy. Deterministic systems still need to enforce authentication, authorization, security invariants, authoritative current state, transactional side effects, and irreversible operations.

Documentation may explain that identity verification is required before a restriction can be removed. Application policy must still enforce it.

That separation is not a limitation of the idea. It is what makes the idea usable.

## The Page May Stop Being the Primary Authored Artifact

The idea that interfaces can be derived rather than handcrafted has real lineage. Server-driven UI, declarative and model-driven systems, configuration-driven interfaces, and other forms of generated composition long predate the current AI wave.

The shift I want to investigate is narrower: **structured product knowledge participating more directly in the derivation**.

A capability-oriented architecture suggests a model like this:

```text
available capabilities
+ current state
+ product knowledge
+ deterministic policy
→ composition
→ interface
```

The page becomes more like a derived view of those inputs.

A shorthand for the idea is:

```text
UI = f(state, capabilities, policy, context)
```

That is a thinking model, not an executable formula, and it is not a claim that every screen should be generated at runtime.

Some experiences require carefully authored interaction design. Some layouts encode important spatial meaning. Predictability can itself be a product requirement.

But enterprise software also contains substantial repeated orchestration: the same trusted capabilities rearranged around different roles, states, products, versions, workflows, and policy boundaries.

That is where declarative composition may earn its place.

If that holds, engineering does not disappear. Its abstraction boundary moves. Developers spend less time hand-authoring every final composition and more time building the capability, contract, policy, validation, and knowledge infrastructure from which safe compositions can be produced.

---

## What Product Knowledge Can and Cannot Own

Restraint is what makes the thesis credible.

Product knowledge must not become a database. It can describe meaning around state; it does not own the current state itself.

It must not become an execution engine. Capabilities execute; knowledge describes intent, relevance, and guidance.

It must not become an authorization system. Permissions are enforced by deterministic systems with real contracts, not by prose.

And it is not a substitute for validation. Knowledge that cannot be reconciled with the systems responsible for the concern can drift, and drifted knowledge can make a context layer confidently wrong.

When representations disagree, the architecture should expose the conflict and ask which artifact owns that concern. Runtime state may settle a question about current facts. Code may settle what the implementation currently does. A governing specification may show that implementation is defective. Product knowledge may need correction if its explanation no longer matches either.

The goal is not to create one universal source of truth. It is to make **authority explicit enough that disagreement becomes inspectable**.

---

## Toward Declarative Product Composition

The conceptual model remains simple:

```text
UI = f(state, capabilities, policy, context)
```

State remains deterministic. Capabilities remain engineered and bounded. Policy constrains what is permitted. Product knowledge and selected context increasingly shape which capabilities are relevant, how they are explained, and how they may be composed into the experience.

None of this removes engineering. It changes where engineering effort concentrates.

The open questions are substantial:

- **Authority levels.** Which product-knowledge artifacts are explanatory, which are normative, and which are merely editorial?
- **Synchronization.** How do code, specifications, policy, and product knowledge stay aligned as each evolves?
- **Dynamic range.** Which parts of composition can safely vary, and which should remain deliberately fixed?
- **Testability.** How do we verify capability selection, knowledge applicability, policy constraints, and allowed compositions?
- **Representation.** Is Markdown only the authoring surface while typed objects, schemas, knowledge graphs, or another model become the machine-facing representation?
- **Inference boundaries.** Where should semantic interpretation stop and deterministic authority begin?

I do not have final answers. That is why this is an architectural exploration rather than a framework announcement.

Software already gives behavior, state, and structure deliberate representations. Meaning has often been more fragmented. What changes now is that product knowledge can increasingly become something software consumes rather than merely something people read.

The interesting endpoint is not a model that can generate more components.

It is the possibility that state, trusted capabilities, deterministic policy, and product knowledge become explicit enough that useful portions of an interface can be **derived without surrendering deterministic control**.

Which leaves the question I think this research has been moving toward all along:

> **If those layers are explicit, how much of the final interface still needs to be authored imperatively?**
