## The Audio Sample Rate Dilemma

Consumer audio hardware and browser `AudioContext` instances commonly operate at **44,100 Hz** or **48,000 Hz** using floating-point sample buffers.

Sending 48 kHz stereo 32-bit float audio directly would produce about **384 KB/sec** of raw sample data before protocol overhead:

48,000 samples/sec × 2 channels × 4 bytes/sample = 384,000 bytes/sec.

<ResearchBreakout mode="wide">
  <AudioFormatReductionVisual />
</ResearchBreakout>

### The Client-Side Downsampling Solution

In `CaptionControl.vue`, downsampling is performed before packet transmission:

<ResearchSourceExcerpt file="CaptionControl.vue">

```javascript
function downsampleBuffer(buffer, inputSampleRate, outputSampleRate = 16000) {
  if (inputSampleRate === outputSampleRate) return buffer;
  
  const sampleRateRatio = inputSampleRate / outputSampleRate;
  const newLength = Math.round(buffer.length / sampleRateRatio);
  const result = new Float32Array(newLength);
  
  let offsetResult = 0;
  let offsetBuffer = 0;
  
  while (offsetResult < result.length) {
    const nextOffsetBuffer = Math.round((offsetResult + 1) * sampleRateRatio);
    let accum = 0, count = 0;
    
    for (let i = offsetBuffer; i < nextOffsetBuffer && i < buffer.length; i++) {
      accum += buffer[i];
      count++;
    }
    result[offsetResult] = count > 0 ? accum / count : 0;
    offsetResult++;
    offsetBuffer = nextOffsetBuffer;
  }
  return result;
}
```

</ResearchSourceExcerpt>

The filtered float array is then clamped and converted to signed 16-bit integers (`Int16Array`). At 16 kHz × 16-bit mono, that format is approximately **32 kB/s (32,000 bytes/s)** before WebSocket overhead—a mathematically derived reduction of about **91.7%** compared with the 48 kHz stereo 32-bit-float example above.

## Buffered Chunking: Delay vs. Linguistic Context

Speech transcription needs enough surrounding audio to resolve word boundaries and linguistic context. That creates a practical trade-off:

<ResearchBreakout mode="wide">
  <ChunkingTradeoffVisual />
</ResearchBreakout>

The public backend currently defaults to a **3-second chunk threshold** when no client override is supplied.

In `fastapi_app.py`, the server uses a fixed-duration chunk accumulator:

<ResearchSourceExcerpt file="fastapi_app.py">

```python
chunk_length_bytes = int(client.config.get("chunk_length_seconds", 3)) * client.sampling_rate * client.samples_width

if len(client.buffer) >= chunk_length_bytes:
    client.scratch_buffer.extend(client.buffer)
    client.buffer.clear()
    asyncio.create_task(self.process_buffer(client, websocket))
```

</ResearchSourceExcerpt>

After transcription finishes, `scratch_buffer` is cleared. Because processed samples are not intentionally retained and reused across overlapping windows, describing this as a sliding window would overstate what the current source implements.

## Handling Low-Confidence Transcription Output

Continuous microphone input can cause Whisper to emit undesirable text during silence, ambient noise, or otherwise low-confidence audio. The public source currently addresses this primarily on the client after transcription.

### Current Backend Behavior

`whisper-api` includes a `VADFactory`, PyAnnote dependencies, and a lazy `get_vad()` helper. However, the current public `process_buffer()` implementation does **not** invoke that VAD pipeline before `model.transcribe()`.

### Client-Side Probabilistic Filtering

In `CaptionControl.vue`, returned segments are evaluated against Whisper metadata:

<ResearchSourceExcerpt file="CaptionControl.vue">

```javascript
function filterSegments(segments) {
  for (let x = 0; x < segments.length; x += 1) {
    const seg = segments[x];
    const noSpeech = seg.no_speech_prob ?? 0;
    const temp = seg.temperature ?? 0;
    if (noSpeech <= 0.6 && temp <= 0.8 && seg.text?.trim()) {
      store.captions.push(seg.text.trim());
    }
  }
}
```

</ResearchSourceExcerpt>

Segments above those thresholds are discarded by the client. This helps suppress likely hallucinated or low-confidence text before it reaches the caption queue, but it does not guarantee that all phantom output is eliminated.

## Async Inference & UI Rendering

The backend uses `asyncio.to_thread()` around `model.transcribe()`, moving blocking inference off the async event loop. The same principle—keep blocking work off the responsive path—applies in the renderer.

`CaptionsView.vue` measures caption geometry after Vue's `nextTick()`, then uses nested `requestAnimationFrame()` callbacks to apply the transition styles:

<ResearchSourceExcerpt file="CaptionsView.vue">

```javascript
const performAnimation = (multiplier = 1) => {
  requestAnimationFrame(() => {
    requestAnimationFrame(() => {
      reference.$el.style.transition = `all ease-in-out ${animationTiming * multiplier}ms`;
      reference.$el.style.opacity = x >= messageRefs.value.length - 1 ? 1 : 0;
      reference.$el.style.transform = `revert`;
      setTimeout(() => {
        if (reference.$el) reference.$el.style.transition = 'unset';
      }, animationTiming * multiplier);
    });
  });
};
```

</ResearchSourceExcerpt>

The current prototype still performs synchronous geometry reads when captions mount, including a second `getBoundingClientRect()` after style changes. That is acceptable as implementation evidence for the current prototype, but it is not presented here as an optimized rendering strategy; a production pass should batch geometry reads before DOM writes to reduce forced-layout risk.
