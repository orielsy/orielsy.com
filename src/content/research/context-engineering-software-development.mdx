Durable project memory solves only part of the coding-agent context problem. As repository knowledge grows, the next challenge becomes selection: determining which architectural rules, component contracts, decisions, specifications, and implementation context are relevant to the task at hand. This exploration looks at the transition from static project memory toward task-aware context retrieval and delivery.

## From Project Memory to Context Selection

[From Prompts to Project Memory](/research/specification-driven-ai-development) focuses on making engineering intent durable across coding-agent sessions. This draft starts from that foundation rather than repeating it.

```text
Project Memory
→ make project knowledge durable

Context Engineering
→ select the relevant durable knowledge for the current task

Repository Context Engine
→ explore an implementation for delivering that selected context on demand
```

The problem changes as durable repository memory grows. A coding task rarely needs every specification, ADR, component contract, convention, and historical implementation detail at once. The useful question becomes: **which context is relevant now, at what scope, and through which delivery mechanism?**

## Selection Questions

This research direction will focus on questions such as:

- **Task awareness:** What does the current coding task actually need to know?
- **Relevance:** Which rules, specifications, decisions, and implementation details are materially related?
- **Scope:** Is the relevant context project-wide, feature-specific, package-specific, or component-specific?
- **Architectural knowledge:** Which invariants and ADRs should constrain a proposed change?
- **Component contracts:** Which interfaces or usage conventions matter without loading entire implementations?
- **Specification selection:** Which feature specs, plans, and tasks should be surfaced for the work being attempted?
- **Delivery:** Should selected context be loaded directly, exposed through tools, or delivered through a protocol such as MCP?

## Retrieval and Delivery Are Not the Same Problem

A future system might use deterministic routing, structured indexes, search, or other retrieval techniques to identify candidate context. Model Context Protocol could provide one delivery surface for that context, but MCP itself does not solve relevance or selection.

No semantic retrieval system, vector database, AST graph, or completed MCP server is claimed by this draft. Those choices remain open until an implementation provides evidence for them.

## Project Counterpart

The unpublished [Repository Context Engine for Coding Agents](/projects/context-engine-coding-agents) is the implementation counterpart to this research direction. It remains a proposed/in-progress project: a place to test how repository-specific context could be delivered to coding agents on demand without presenting unbuilt capabilities as finished tooling.
