A conversation can hold a correction while an agent is working. A later session may see the repository without that conversation. The useful question is not how to keep every prompt alive, but which consequential decisions should be written beside the work they govern.

Here, **spec-driven** names a repository practice in which specifications own product requirements. It does not make a specification universally authoritative: constitutions preserve project-wide constraints, ADRs preserve rationale, plans and tasks preserve approach and execution state, code shows implementation, and tests show what was checked.

Version-controlled memory improves recoverability, not correctness by default. A future agent must still find and interpret the relevant records, inspect implementation evidence, and verify behavior.

## The Unsupported Claim Came Back

A sentence on my homepage once described my experience as including **design systems**, a broader claim than the evidence established.

Correcting the sentence fixed the visible output. Recording the boundary in the repository created two durable addresses for later work: the [project constitution](https://github.com/orielsy/orielsy.com/blob/main/.specify/memory/constitution.md) blocks unsupported project-wide positioning, while the [site-foundation specification](https://github.com/orielsy/orielsy.com/blob/main/specs/001-site-foundation/spec.md) applies that boundary to this site.

The current branch shows those guardrails. It does not, by itself, prove the complete earlier conversation or every step in the correction's chronology. A later agent now has a durable address for the distinction; that makes recurrence less likely, not impossible.

## Conversation Context Is Not Project Memory

Working context is useful while a task is in progress, but later work cannot assume that the same conversation remains available. Consequential constraints, requirements, implementation plans, execution state, and rationale need durable addresses at the scopes they govern.

Code and tests remain adjacent evidence of implementation and verification rather than records of that intent.

The claim remains deliberately narrow: a repository can make intent recoverable without making an agent correct.

## Different Questions Need Different Evidence

A constitution states project-wide constraints. A feature specification states required behavior. A plan describes an approach. Tasks record execution state. An ADR preserves rationale. Code exposes current behavior, and tests show what has been checked.

These sources are related, but they are not interchangeable. There is no automatic universal precedence order. When a requirement, decision, and implementation disagree, name the conflict and investigate it rather than treating whichever file looks most recent as the winner.

## Route Into Memory Instead of Copying It All

[AGENTS.md](https://github.com/orielsy/orielsy.com/blob/main/AGENTS.md) stays deliberately thin. It routes the agent toward the constitution, relevant feature specification, plan and tasks, and ADRs before structural changes. It also says to update durable requirements when they change.

Its role is routing, not storing every rule as a mega-prompt.

Routing can bring both project memory and adjacent implementation evidence into the task. Selecting code or tests does not turn them into records of intent; it makes comparison possible.

For a publication task, the relevant gating requirements and decisions matter more than every unrelated document in the repository. This selection is deliberate reading, not an automated relevance engine.

## Publication Gating Crosses Artifact Boundaries

The [publication-gating specification](https://github.com/orielsy/orielsy.com/blob/main/specs/003-content-publication-gating/spec.md) requires new entries to fail closed. The content schema defaults `published` to `false`. The detail route conditions unpublished body preview on development plus an explicit preview mode. The RSS feed selects published entries.

These are complementary observations, not four interchangeable proofs.

The same concern also covers collection cards, direct status pages, indexing, and local preview. The figure samples the evidence chain rather than certifying that every acceptance criterion is met.

## Updating the Rule Is Part of the Change

When unpublished cards moved from non-clickable summaries to inline status interactions, the requirement did not live in the component alone. The feature specification, publication decision, README, and URL/SEO policy came to describe the new behavior. Repository history supports these updates; it should not be flattened into a claim that all artifacts changed in a single commit.

This is a **coordinated maintenance workflow across owners**: update the records that own the changed requirement and rationale, update the implementation, then inspect and verify the resulting behavior. A specification is authoritative for the requirement, not a passing test; code shows what exists, but does not retain every reason behind the choice.

## Durable Memory Can Preserve a Disagreement

The [manual-production-publishing ADR](https://github.com/orielsy/orielsy.com/blob/main/docs/decisions/003-manual-production-publishing.md) centers a local `npm run live` path and says a repository-authored GitHub Actions workflow was not required for that model.

Current guidance and the workflow file document additional paths. Both accounts are inspectable, but persistence did not reconcile them.

The current operational guidance and historical decision record answer different questions. The conflict should be surfaced for human review; this article does not silently declare which document supersedes the other.

## Memory Needs Maintenance; Relevance Remains Open

Wrong specifications remain wrong. Documents can drift, agents can misread explicit context, and overlapping guidance can create noise. Implementation evidence can also be incomplete: code shows what exists on inspected paths, while tests show only what was checked.

The defensible conclusion is narrow: durable records let later work recover intent and rationale, then compare them with implementation and verification evidence. Tests and review are still needed. The practical gain is that consequential decisions have an address and silent regression becomes less likely.

An unpublished **Repository Context Engine for Coding Agents** concept proposes task-aware selection and explicit delivery of repository context. That is a future research direction, not an implemented engine. For now, the selection pictured here is explicit and human-authored.
